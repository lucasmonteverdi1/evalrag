# Notes and remarks on the project for better personal understanding during development

This project is a tool that measures if a RAG system answers correctly. 

**RAG system flow:** question → get relevant documents (chunks) → generate answer.

What this project aims to determine if that generated answer is **reliable**, initially measured
by 3 metrics: faithfulness, 

## Faithfulness
"Is everything that the answer claims backed by the documents, or did the model invent anything?"

### Example
* Retrieved document: "Paris is the capital city of France."
* RAG response: "Paris is the capital city of France. It has a population of 5 million people."
* The first phrase is backed by the document, the second one was "invented" (not contained in the document).
* Faithfulness: 1/2 phrases = 0.50

### How is it measured
1. `decompose_claims()`: the answer is split into individual phrases, each one being an affirmation to verify.
2. The affirmations and the documents are sent to the judge LLM, and it's asked, 
for each affirmation, "Is it backed by these documents? Yes/no." 
3. `parse_verdict() + score`: We read the judge's response on the claim (the `supported` boolean field). 
Based on that, we calculate the score as the sum of supported claim divided by the total claims. 

### Stubs, FakeProvider y labels
Before spending money on calling LLMs, we want to test if the code actually works. 
**Stubs:** 4/5 handwritten examples (question + answer + documents) that we know how they'd have to score.

**FakeProvider:** A "fake judge" that doesn't go on the internet, returns predefined answers. 
This way, tests are free, fast and consistent.

**Labels:** on each stub, we type by hand the "truth" (which phrases are backed and which ones are not), 
and from there we generate what the fake judge should answer. This way, they are never out of sync.

## Validation
A relevant concept is confusion here. The `confusion()` method takes 2 arguments, which are lists of booleans.
The first list corresponds to the human verdicts, and the second one to the judge's verdicts on whether each claim is supported or not.

The lists are generated by putting together all the claims in the stubs and their verdicts. The list looks like this:

                claim1  claim2  claim3  claim4  claim5 ...
human (truth): [True,   True,   False,  True,   False, ...]   ← handwritten labels
judge (model): [True,   False,  False,  True,   True,  ...]   ← LLM verdicts

Both lists have the **same length**, and for the same position ("i"), both refer to the verdict for the claim "i".

The relevant question regarding these lists is **how alike are they?**

### Confusion Matrix
2x2 matrix that classifies each metric based on the 2 opinions (human and LLM).

|                  | Judge says True          | Judge says False         |
|------------------|--------------------------|--------------------------|
| Human says True  | TP (both: sí)            | FN (human yes, judge no) |
| Human says False | FP (human no, judge yes) | TN (both: no)            |

The 4 variables in the `Confusion` class count how many of each case are there on each cell of the matrix.
- TP (true positive): Both say it's backed. ✅
- FP (false positive): the judge said the claim was backed when it wasn't. It "believed" an invented claim. 
- TN (true negative): Both say "not backed". ✅ 
- FN (false negative): The claim was actually backed but the judge said it wasn't. The judge was "too strict". 

Here, the **positive class** would be "True", meaning that the claim is supported. This allows us to define
the F1 score (how good we are at detecting the positive class).

### Cohen's kappa
Percentage of agreement but corrected by chance. **Example:** if 90% of the claims are backed, a "dumb" judge that always answers "True" would get 90% accuracy 
without any real judgment. It was chance, because the majority class dominates.

`kappa = (po − pe) / (1 − pe)`
- po: observed agreement
- pe: expected agreement by chance (90% in the example) 

**Interpretation**
- kappa = 1.0 → perfect agreement
- kappa = 0.0 → they only agree on what luck/chance would predict (judge adds no value)
- kappa < 0 → lower agreement than chance
- Typical ranges: >0.8 excellent, 0.6–0.8 good, <0.4 poor.

Quick note: based on these results, the math on the example scenario would result `pe = 0.9`, but then `po~0.9`
also, which would result in `kappa = 0`, proving that the judge is useless.  

What is actually measured is: "from the agreement NOT explained by chance, what was the score?"

## Runner
Piece that generates `EvalCase`s automatically from real questions.

### The 3 pieces
- `PipelineAdapter` (The contract): Allows extensibility. The runner doesn't know how the user's pipeline
is implemented, it only asks for `run(pregunta) → (chunks, answer)`. 
**Anyone** can connect their pipeline just by implementing that function.
- `run_pipeline` (the loop): it loops the questions calls the adapter for each one and builds the `EvalCase`s.
- `FakePipelineAdapter`: deterministic fake pipeline adapter for testing purposes. 
questions → [runner] → EvalCases → [scorer] → MetricResults

**Important: Separation of concerns** 

The runner does not rank on purpose, it keeps responsibilities separated. 
The CLI will orchestrate `runner → scorer → report`
